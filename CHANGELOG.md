# Changelog

## Unreleased

- Query-text retention cleanup no longer deletes recent rows. It selected rows by `ctid`, which is unique only within one partition of `pgss_queryid_queries`, so each batch also removed rows at the same position in other partitions (postgres-ai/postgresai#495).
- D001 "Logging settings": the box reporter now writes a D001 file, and the CLI's file holds the same facts.
  - `data`: every `log_*` and `auto_explain.*` setting, `logging_collector`, both preload lists and `deadlock_timeout`, with `pg_settings.context` (read from the node).
  - New `logging`, beside `data`: each setting's source; role, database, role-in-database and all-role values of these settings and of `statement_timeout`; login roles with their open sessions; per role, the statements whose longest call reached 1 s, 10 s, the node's own thresholds or values stored per role and per database; temporary files, their bytes and autovacuum runs (box: the last 7 days from monitoring, with autovacuum runs a floor: per table, without tables past rank 100, a table's first reading, or runs counted only on a partition root; CLI: since the statistics reset).
- The pgwatch metric `pg_database_wraparound` now reads every valid database, `template0` included (postgres-ai/postgresai#490). It accepts no connections, but Postgres sets the wraparound limit from the oldest `datfrozenxid` of all databases. A database left invalid by an interrupted `DROP DATABASE` stays out, as Postgres leaves it out of that limit. A box gets the fix when it moves to the release that carries it.
- H001 "Invalid indexes":
  - `index_definition` comes from the metric's own label when the sink database has none (it read "Definition not available").
  - The invalid-index metric gains `is_ready` (`pg_index.indisready`: false means writes do not maintain the index) and `build_in_progress` (a `CREATE INDEX` for it is running, `pg_stat_progress_create_index`). Both are in the report only when the box collects them, never defaulted.
  - New per index: `first_seen_time` / `last_seen_time` (its first and last monitored reading in the last 35 days) and `listed_hours` against `reading_hours` (hourly steps that listed it, against steps with any reading of the database), so a report can tell a leftover from a build that is still running. New per database: `monitoring_start_time`.
  - New metric `pg_not_valid_constraints` (constraints added `NOT VALID` and never validated, system schemas excluded, with each one's type, definition and whether it is a partition's copy of a parent's constraint) and the H001 field `not_valid_constraints`. A `$total$` row keeps "not collected" apart from "none". A database with such a constraint and no invalid index is now reported too.
- G003 "Timeouts, locks, deadlocks" (postgres-ai/postgresai#485):
  - Monitoring boxes now upload a G003 file. It reads as the CLI's, with the settings from A003.
  - New in the box's file and the CLI's: `roles` (the timeouts stored per role and per database, whether it logs in, its calls and longest completed call), `database_settings`, `server_settings` (the value a session starts with, and its source), `routines` (procedures, and functions that set a timeout: whether they commit or catch a cancel). No other setting is copied.
  - New in the box's file only: `deadlock_window` (deadlocks over the last 7 days from the counter's rises, per day and peak hour) and `lock_waits` (who blocked whom, by statement pair).
  - A fact that cannot be read is left out with its reason (`*_error`), never written as none. G003 failing costs no other report.
- The pgwatch metrics `unused_indexes`, `rarely_used_indexes`, `redundant_indexes` and `pg_invalid_indexes` (and the CLI's express checks that run the same SQL) now set `supports_fk` for an index that backs a foreign key (postgres-ai/postgresai#476). The flag compared the table the key points to, by name, and an opclass prefix: an index backing a key read false unless its own table was also referenced, an index on a referenced or self-referencing table read true, and mixed-case or other-schema tables never matched. It now checks that the key is on the index's own table and that the key's columns lead the index, by oid.
- The pgwatch metrics `redundant_indexes` and `index_definitions` (and the CLI's express H004, which runs the same SQL) no longer pair indexes on different columns or with different operator classes (postgres-ai/postgresai#482). An index matched a covering index when its column numbers and opclass OIDs were a text prefix of the other's, so on a table with 10 or more columns an index on column 1 was reported as redundant to one on (column 12, column 3), and opclass OID 1978 matched 19781. The prefix now has to end on a whole column and a whole opclass.
- F004 "Autovacuum: heap bloat (estimated)": each bloated table now also carries what tells dead tuples from free space, for CheckupLoop's F004 report: live and dead tuples, its own autovacuum trigger, autovacuum and manual vacuum runs and inserts, updates and deletes over 7 days, its last vacuum (`vacuum_recorded` false: none since the statistics began), whether autovacuum is off on it, its heap and TOAST size, and the lowest and highest estimate and heap size over the window. Each database has a `history` (the total estimate today and on each of the last 7 days, and the first reading's time) and `autovacuum_settings` (the server's `autovacuum_vacuum_threshold` and `autovacuum_vacuum_scale_factor`, behind each table's trigger). A fact is null when its metric cannot be read. Not covered: an old-style inheritance parent (pgwatch sums its children into its row).
- pgwatch `table_stats.no_autovacuum` now sees `autovacuum_enabled = false` (and `no`, `0` and their prefixes). Postgres stores a reloption as typed, and the metric matched only `autovacuum_enabled=off`, so a table with autovacuum turned off the common way read as on in F001 and F004. A box gets the fix when it moves to the release that carries it (the configs volume is filled from that release).
- H004 "Redundant indexes":
  - Each candidate's `index_definition`, and the definition and size of each index in `redundant_to`, now come from the metric's own labels (`index_definition`, `redundant_to_json`) when the sink database has none. Before, every definition read "Definition not available" and every covering index had size 0, so no pair could be checked.
  - `database_size_bytes` is matched by the database's own name (`real_dbname`): the redundant-index series carry pgwatch's source name, so the size was 0 on managed platforms. The entry is now keyed by the database's name, as H002's is.
  - New per candidate: `index_usage_first` with `index_usage_first_time` (its scan counter at its first monitored reading in the last 35 days) and `index_usage_last_time` (the reading `index_usage` comes from), so a report can say how many counters rose between two dated readings. New per database: `usage_readings`, the span of those readings and whether a restart or a statistics reset falls inside it.
  - New `also_unused` on each candidate and each covering index: whether it is also on the unused-index list (H002). Omitted when that list cannot be read.
  - Each candidate is listed once, from its latest series (postgres-ai/postgresai#483). The metric starts a new series each time a covering index grows, so two collections in the 3-hour lookback listed the candidate twice (counted twice in `total_size_bytes`), and `table_size_bytes`, `index_usage` and `supports_fk` could come from a different series than the row. They are now read from the candidate's own series.
- H002 "Unused indexes" (postgres-ai/postgresai#475):
  - `supports_fk` and `idx_is_btree` now come from their pgwatch series. They were read as labels that do not exist, so every index was reported as backing no foreign key. An index the series does not cover gets `null` (unknown), never `false`.
  - `index_definition` falls back to the metric's own definition when the sink database has none, so the undo statement is known.
  - `stats_reset` is read by `database_name` as well as `datname` (pgwatch labels it `database_name`); it was always null.
  - New `scan_window` per database: the first monitored reading of the unused-index list in the last 35 days to now, in days, and whether a restart or a statistics reset falls inside it. Each index gets `zero_scans_since`: the list holds only indexes with no scans, and the counter only grows, so an index in every reading had no scans in between.
  - New `table_writes`: updates, HOT updates (they write no index entries) and inserts over that window, per table holding a candidate.
- F001 "Autovacuum: current settings": the report now also reads `maintenance_work_mem`, `log_autovacuum_min_duration`, `autovacuum_vacuum_insert_threshold`, and PG18's `autovacuum_vacuum_max_threshold` and `autovacuum_worker_slots`, and carries new optional fields for CheckupLoop's F001 report (postgres-ai/platform-all#1112, #471):
  - `autovacuum_workers`: mean and peak active workers over 7 days, with the sample count and the limit.
  - `autovacuum_tables`: application tables of 1 GiB or more, and tables with dead tuples, the most overdue first. Each row has its size, live and dead tuples (now and 24 h ago), its own vacuum threshold, autovacuum runs in the window, its last vacuum, and whether autovacuum is off.
  - `autovacuum_scope`: the full counts behind that list.
  - `settings_changed_in_window`: the autovacuum settings that had more than one value in the window.
  - `autovacuum_runs_top`: the most vacuumed tables.
  - `autovacuum_runs_window_seconds`: the window both run counts cover (7 days).

  These come from both F001 paths, from A003 and the fallback. System catalogs, pgwatch's `$other$` row and excluded databases are left out, and a field is omitted when its metrics cannot be read.
- A014 "Resource sizing": each `series.disk_iops` point is now the 5-minute average of read + write IOPS, as `disk_mbps` already was, not the busiest minute, so `disk.iops_p95` and `disk.iops_max` are the 95th percentile and the highest of those averages. The report says so in a new field, `series.disk_iops_kind: "avg_5m"`; the platform judges IOPS against the compute size's sustained limit only when it is present, since older reports carry busiest-minute points (postgres-ai/platform-all#1086). Supabase disk IOPS and throughput (`host_disk_read_iops`, `host_disk_write_iops`, `host_disk_read_bytes_per_second`, `host_disk_write_bytes_per_second`) sum every block device, root disk included: a compute size's IOPS and MB/s limits are the instance's EBS limits, which cap all attached volumes together.
- New reporter check A014 "Resource sizing": each daily report now carries how much CPU, memory, disk throughput and IOPS the database server used over the last 7 days (or since data began), plus backends against `max_connections`, database size and a 5-minute series. It is measurements only: the platform compares them with the project's Supabase compute size and shows whether it is undersized, right-sized or oversized in the health matrix (postgres-ai/platform-all#1051). CPU, memory and disk need host metrics; without them those fields are null.
- `prepare-db` refuses extensions and predefined-role-owned objects inside the `postgres_ai` schema, including objects with no ownership dependency row. Schema refusal errors now give DBA remediation in the CLI and render database-provided Detail and Hint on one terminal line.
- `prepare-db` no longer refuses on ClickHouse Managed Postgres with "postgres_ai schema grants CREATE to another role". ClickHouse Cloud's default privileges grant CREATE on every new schema to `chpg_console_admin`, so the schema prepare-db had just created was refused at once. When prepare-db creates `postgres_ai` itself, it now revokes CREATE from every role other than the owner. A schema that already exists is still refused while another role can create in it (postgres-ai/postgresai#469).

- Dashboard "06. Replication and HA" replaces the placeholder with primary-side streaming replication panels read from `pg_stat_replication`.
- `pgai mon deploy --reset-password` no longer refuses because of instances that cannot be using `postgres_ai_mon`: a deleted self-hosted instance (status `deactivated`, which is what `pgai mon instances delete` leaves) and a cloud launch that failed before its box registered. Before, any such instance without a known server blocked every password reset in the organization, and deleting it did not help. When instances in the refusal share a name, the message gives their ids and the delete commands use the ids, since `pgai mon instances delete <name>` refuses an ambiguous name. When the database itself is already monitored, the message names that instance as the platform does and ends with the delete command, then says to run the deploy again with `--reset-password`.
- Helm chart: the Grafana datasource ConfigMap no longer contains the sink Postgres password or the VictoriaMetrics basic-auth password. Grafana reads them from the chart Secret (keys `postgres-password` and `vm-auth-password`) through environment variables. **Upgrade:** installs that use `existingSecret.name`, `nameOverride` or `fullnameOverride` must set `global.postgresAiSecretName` to the chart Secret name. Without it, `helm upgrade` stops at render, before it changes the cluster, and the error message gives the correct name. Installs with the default Secret name need no other change. Do not upgrade any install, default name included, with `helm upgrade --reuse-values`. It drops the new Grafana env defaults, and the upgrade stops at render. Use `--reset-then-reuse-values` (Helm >= 3.14) or pass the values file again.
- The reporter's first run starts 3 minutes after the stack starts, not 30, and then waits for data: it polls Prometheus every 15 s until every enabled target in `instances.yml` has `settings` and `db_stats` samples, for at most 30 minutes, then runs. A first collection has no fixed time bound (some metrics run for minutes, and a failed first connect retries after 120 s), so the run waits for the data, not a clock. When no target has data at all, the run does not upload the empty `local` fallback report (it would read as "no issues"); it logs why, and the next run retries. `mon targets add` restarts `postgres-reports`, so a target added later gets its first report after the same delay and wait, not the next day (`remove` does not). A failed run is retried after 30 minutes instead of exiting, which made the container restart and run again every few minutes. `REPORTER_INITIAL_DELAY_SECONDS`, `REPORTER_READINESS_TIMEOUT_SECONDS` (0 turns the wait off), `REPORTER_READINESS_POLL_SECONDS` and `REPORTER_RETRY_SECONDS` override the defaults. Later runs stay daily.
- One host metrics vocabulary for RDS, Supabase and ClickHouse Managed Postgres. A new `vmalert` service evaluates `config/prometheus/host_rules.yml`, which maps Supabase `node_*` and ClickHouse `PostgresServer_*` series to the `host_*` names, units and `cluster`/`node_name` labels that `rds-host-stats` writes (table in `docs/host-metrics.md`). `vmalert` runs under the `host-metrics` compose profile, which `mon targets add` and `mon targets remove` keep in `COMPOSE_PROFILES` only while a ClickHouse or Supabase target has host metrics; a stack without one, or with RDS only, does not run it. Supabase host series now carry the pgwatch `cluster`/`node_name` of the Supabase target in `instances.yml`. Dashboard 1 gains one collapsed "Host" row near the end of the page, with CPU, memory, storage, disk IOPS and network panels read from `host_*` only; every panel has data for each of the three providers, and a self-managed node sees it closed and empty. RDS and Aurora DB load from Performance Insights (`host_db_load`) has its own collapsed row after it, empty on other providers and on RDS without Performance Insights.
- Added Dashboard 99. Host stats (uid `host-stats`). It shows the Dashboard 1 Host panels on a separate page, open, with RDS and Aurora DB load from Performance Insights in a collapsed row below them. Its cluster and node selectors read `host_*` series only. It is empty on self-managed nodes and on the Helm chart. The Host row on Dashboard 1 stays.
- `instance-jobs` now reports the upstream HTTP status inside `failure_class`: a failed DBLab call comes back as `engine_error_404` / `engine_error_500` rather than a flat `engine_error`, and a failed Joe call as `joe_error_<code>`. The Console showed an endless spinner when a deleted clone was opened, because the engine's 404 arrives as a failed job inside an HTTP 200 and the only way to tell it from a broken engine was to regex the English error text. The text itself is unchanged, and a failure with no HTTP status behind it (timeout, cancelled, engine/joe unreachable, bad args, oversize reply) keeps its existing flat class. (postgres-ai/platform-all#861)
- `postgresai promql` accepts `--project <id|alias>` to pick the monitoring instance by project id, alias or name instead of its UUID, the same way `joe` and `dblab` do. It resolves through `projects_list`, so it needs a platform that reports `monitoring_instance_ids` there; on an older one it says so and asks for `--instance`. A project with several active monitoring instances is refused with their ids listed, rather than guessing which one you meant, and so is a name or alias that matches more than one project.
- Added `rds-host-stats`, a service for the Docker Compose monitoring stack (profile `rds`) that polls one RDS or Aurora PostgreSQL instance's host metrics from CloudWatch, Performance Insights (DB load) and Enhanced Monitoring and writes them to VictoriaMetrics as `host_*` series with the pgwatch `cluster` and `node_name` labels. Set `RDS_DB_INSTANCE_IDENTIFIER` and `AWS_REGION`, and `RDS_ROLE_ARN` with `RDS_EXTERNAL_ID` to read through a customer's read-only role. The container reserves half a CPU. On a configuration error it logs the error once and idles until it is recreated, so a bad `.env` does not put the service into a restart loop. CloudWatch and Performance Insights buckets are written only once they have closed for a full period, so a partially aggregated minute is never frozen into the series.
- The `instance-jobs` container can now be turned on for a machine through a supported switch instead of a hand-run `docker compose --profile`. `postgresai mon local-install --instance-jobs` (or `PGAI_INSTANCE_JOBS`, or `instance_jobs_enabled` in the ansible role) writes `COMPOSE_PROFILES=instance-jobs` into the stack `.env`, which is what compose reads by itself — so `mon stop` / `mon start` / `mon update` / `mon status` all cover the container from then on, and `mon health` reports an absent one as a fault rather than as `- not enabled`. Passing nothing expresses no opinion, so an upgrade never opens or closes the channel, and any other profile listed in `COMPOSE_PROFILES` is preserved. Turning it off removes the container as well as the profile — taking the profile out of `.env` does not stop one that is already running. The platform's `app.settings.instance_jobs_enabled` is still a separate gate: with it off, a running container is handed no work.
- Closed VictoriaMetrics' administrative endpoints on the Docker Compose monitoring stack. `sink-prometheus` now runs with `-deleteAuthKey`, `-snapshotAuthKey`, `-forceMergeAuthKey` and `-pprofAuthKey`, minted per install and stored in `.env` as `VM_DELETE_AUTH_KEY`, `VM_SNAPSHOT_AUTH_KEY`, `VM_FORCE_MERGE_AUTH_KEY` and `VM_PPROF_AUTH_KEY`. Grafana's datasource proxy filters POST but forwards every GET, and VictoriaMetrics required no key while these were unset, so any Grafana Viewer — including the `pgai-aas-collect` service account — could delete the whole metrics history through the proxy. `-pprofAuthKey` is part of the fix rather than extra hardening: `/debug/pprof/*` was reachable with the credentials the proxy already supplies, and `/debug/pprof/cmdline` served the process arguments, which is where the other keys used to live. Both halves are now closed — pprof requires its own key, and every secret is passed as `file://` so none of them appears in the container command line, which is what `/debug/pprof/cmdline` and the host process table expose. The keys are still container environment variables, so `docker inspect` shows them; that needs access to the Docker socket, not a Grafana Viewer token. `mon update` and `mon update-config` add the keys to an existing `.env` and then bring `sink-prometheus` in line with the compose file, because the flags live on the container command line and `mon restart` (`docker compose restart`) re-runs the container exactly as recorded. That step is driven by the running container's config rather than by what the run happened to add, so a failed attempt is retried next time; it is skipped when the service is not running, and it uses `--no-deps` so it cannot re-seed a live-patched `prometheus.yml`. Nothing that reads metrics receives the keys. **Scope:** this covers the Docker Compose stack and the Terraform AWS deployment. The Helm chart and the preview stacks are unchanged and still affected.
- Fixed index health checks recommending that built-in catalog indexes be dropped. H001 (invalid indexes), H002 (unused indexes) and H004 (redundant indexes) — and the `unused_indexes`, `redundant_indexes`, `rarely_used_indexes` and `index_definitions` pgwatch metrics behind them — no longer report indexes in `pg_catalog`, `information_schema`, `pg_toast` or per-backend temp schemas. Such indexes cannot be dropped, so recommending their removal was always wrong; `pg_catalog.pg_class_tblspc_relfilenode_index` was the case that surfaced it. Expect a one-off step drop in unused/redundant index counts and total sizes on the first report after upgrading: the catalog rows that were being counted are simply gone. Bloat (F004/F005) and wraparound (F002) still include catalogs on purpose.
- Fixed express checkup on databases without the optional `postgres_ai` schema. F004/F005 now degrade with machine-readable status and warning summaries instead of reporting a misleading healthy empty result.
